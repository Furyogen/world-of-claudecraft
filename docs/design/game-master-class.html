Mockup, not implemented

Game Master: a staff-only tenth class

A tenth PlayerClass that only an account carrying staff roles can roll. Game Masters are not fighters. They have no health, no resource, no level, no gear, and no attack: nothing in the combat system can address them, and they cannot address it. Their spellbook is the moderation command set, and casting an entry opens a parameter window that emits the exact chat command the server already parses today. The class color is pure black, #000000.

1. Character creation

The staff tile appears at the end of the class grid, and only for an account the auth response marks as staff. Everyone else never receives the tile in their payload, so it cannot be revealed by editing the DOM.

Where the other nine classes show stat bars and a starting kit, this one shows nothing to show. The class-details panel deliberately renders the empty state rather than a row of zeroes: a Game Master has no stats, not stats that happen to be zero.

2. In-world chrome

Pure black is the class color everywhere the palette is read: portrait ring, nameplate, party frame dot, minimap blip, chat name. On the dark HUD that reads as absence, so every text-bearing surface pairs the black with a thin gold rim (see the contrast note below). The unit frame is the first place the non-combatant rule shows up.

Ashvane GM Non-combatant Untargetable Visible No health bar. No resource bar. No level. Presence and spectate state are the only things this frame tracks.

The frame keeps the shape every unit frame has, so the HUD needs no special case, but the two bar slots are empty by design. A Game Master has nothing to deplete: the only live state worth a player's or an operator's attention is whether they are currently visible and whether they are spectating someone.

5. The non-combatant contract

Game Masters do not fight. That is a hard rule, not a balance choice, so it is worth writing as a list of things the sim must be able to state plainly. Every line below is testable.

RuleWhat it means
Cannot attackNo auto-attack, no abilities that deal damage or healing. The spellbook holds commands, so there is nothing to point at a target.
Cannot be attackedNot a valid target for any hostile ability, player or mob. This is stronger than invulnerability: the target-selection path never offers them, so a player cannot even begin a cast.
Generates no threatMobs do not acquire, path to, or leash toward a Game Master. They are not in the aggro system at all.
No health, resource, or levelNothing to deplete and nothing to grow. No XP, no gear, no talents, no stat block.
No loot or creditNever rolls on loot, never takes quest or deed credit, never counts toward a group size or a dungeon lockout.
Excluded from every ladderNot queueable for arena, Fiesta, Yumi, dungeon finder, or battlegrounds, and never appears on a leaderboard.
Commands are not spellsA command has no cast time, no range, no line of sight, and no cooldown. It is rate limited and written to the moderation log, which is a different thing from a resource cost.

Today a staff character is an ordinary combatant with gm set: invulnerable in src/sim/combat/damage.ts, and shoved to the level cap on join in server/game.ts so it is not one-shot. Both of those are patches over the wrong default. If the class is outside combat, invulnerability becomes a consequence rather than the mechanism, and the level-cap shove can go away entirely: there is no level to protect.

6. Notes and open questions

Contrast: pure black on a dark HUD

#000000 against the panel base #15151f is roughly 1.3:1, far under the WCAG 2.2 AA 4.5:1 the HUD chrome contract requires. The mockup keeps the class color exactly #000000 for fills (swatch, portrait ring, minimap blip) and pairs it with a #d8c07a rim wherever it carries text or an edge, the same trick Priest (#fffff0) needs in the opposite direction. The alternative, lightening the class color itself, is not on the table: the request pins pure black.

Why it is a class and not a toggle

  • Staff already have a gm entity flag and an admin dashboard. The class is what makes the authority visible in-world: the black nameplate is a uniform, so players can see who acted.
  • Reusing the class seam means the spellbook, action bar, keybinds, and macros work with no new UI plumbing. A command row drags onto the action bar exactly like an ability.
  • It also gives the non-combatant rule somewhere to live. As a toggle on a Warrior, "does not fight" is a pile of exceptions scattered through the combat code. As a class, it is one predicate the combat, threat, loot, and queue paths each ask once.

Two ways a row opens, decided by the target

A command that acts on a player (any row with a Name field) reads the target the same way an ordinary ability does:

  • With a target: the window leads with "Are you sure you want to silence Thornbeak?" and the buttons are Yes and No. The Name field is not rendered at all, because the target already answered it. Rows that still need a duration (Silence, Bind, Sever, Still) keep those fields under the question; everything else is a straight yes or no.
  • With no target: the window is the plain form, asking who to act on, with Apply and Cancel.
  • Irreversible rows ask either way. Excommunicate carries a confirm flag, so submitting its untargeted form does not send: it turns into the same question, naming the player just typed. That flag is honored in both paths rather than being copy that promises a confirmation nothing implements.

Rows that name no player (Return, Proclaim) never show the question, since there is nothing for a target to disambiguate.

Still open: Return takes no arguments at all, yet selecting it opens a window whose only content is "This command takes no arguments." A zero-argument row should almost certainly just fire on click like an instant ability, and the window should be reserved for rows that have something to ask.

Open question: what does the world see

A Game Master who cannot be attacked and cannot be targeted is close to a ghost, which raises a question this mockup does not answer: should they be visible by default at all? The frame above shows a Visible chip because the choice belongs to the operator, but the defaults are worth deciding deliberately. Standing visible is a moderation tool in its own right, and standing invisible is the honest state for observation. Spectate already implies the latter.

What the real implementation touches

  • src/sim/types.ts: a tenth PlayerClass member, plus a decision on whether it joins ALL_CLASSES (it should not, that list drives content tables, quest reward maps, and the class-balance suites).
  • src/sim/content/classes.ts: a ClassDef with an empty abilities array and color: 0x000000. The shape itself pushes back here, since it requires baseStats, startWeapon, and a resourceType that a non-combatant has no answer for. Either those fields become optional or the class carries an explicit combat: false that every consumer checks before it reads them; filling them with zeroes and a bare fist is the outcome to avoid, because it teaches the rest of the code that a Game Master is a very weak fighter rather than not a fighter.
  • src/sim/: one isCombatant predicate the damage, threat, targeting, loot, and queue paths each consult, so the non-combatant table above has a single implementation instead of seven. This is the part worth getting right, and it belongs behind the SimContext seam rather than inside sim.ts.
  • src/ui/: a pure gm_command_view.ts holding the command catalog and argument validation (the DEV_COMMAND_ACTIONS shape in src/ui/dev_command_view.ts is the exact precedent), plus a thin gm_command_window.ts painter. The spellbook branches on the class to render command rows.
  • server/: the create-character route re-checks staff roles; the WS command path is unchanged, because the window sends the same chat command a typing GM would.
  • Tests: the class-content pins, an IWorld parity update if the window needs a new facet member, a negative test proving a non-staff account is refused the class at character creation even with a forged request, and one test per row of the non-combatant table (a mob that never acquires, a hostile cast that cannot select the target, a kill that yields no loot roll).
